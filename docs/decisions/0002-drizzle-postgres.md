# 0002: Postgres with Drizzle ORM and committed migrations

- **Status:** Accepted
- **Date:** 2026-11-22

## Context

Products need a relational database with real constraints, typed queries, and schema changes that are reviewable in a PR. Hosting should be serverless-friendly and have a free tier (Neon or Supabase).

## Decision

- Postgres is the only database.
- Drizzle ORM for queries, drizzle-kit for migrations. The driver is `pg` (node-postgres) through `drizzle-orm/node-postgres`.
- Each module defines its tables in `<name>.table.ts`. Migrations are generated by `pnpm db:generate` into `src/platform/db/migrations` and committed in the same PR as the table change.
- Repos take a `Db` handle typed as Drizzle's driver-agnostic `PgDatabase`, so the same repo code runs on PGlite in tests (ADR 0006).
- Only repos, table files, module `index.ts` wiring and `src/platform` may touch the database (`db-access-only-in-repos`).

## Alternatives considered

- **Prisma:** good DX, but a generated client and its own schema language are more moving parts, and it has no in-process Postgres story for tests.
- **Kysely or raw SQL:** fine, but no migration generation from the schema.
- **postgres.js driver:** equally capable. `pg` is the Postgres peer dependency of Better Auth and the driver the Vercel and Neon pooling guides use.
- **SQLite / Turso:** simplest to run, but weaker constraints and a different dialect from where products usually end up.

## Consequences

- Schema is code, reviewed like code. A table change without a migration is visible in the diff.
- Drizzle is pre-1.0 (0.45 at the time of writing; a 1.0 release candidate exists). Expect one deliberate upgrade.
- No relational query API (`db.query`) is set up; repos use the SQL-like builder. Add it per product if wanted.

## How to reverse it

Repos are the only code that knows about Drizzle. Replacing it means rewriting each `*.repo.ts` and `*.table.ts` behind the same repo types. Services and tests with fake repos do not change.
